# PULSE design review

**Review scope:** `docs/PRODUCT_SPEC.md`, `docs/DESIGN_SYSTEM.md`, `docs/FEASIBILITY_REPORT.md`, `docs/AUDIO_ENGINE.md`, `docs/SENSOR_ENGINE.md`, `docs/ARCHITECTURE.md`, `docs/API_AND_DATA_MODEL.md`, `tasks.md`, and the repository state observed on 2026-10-24. The repository-state statements below describe that historical review snapshot unless they are explicitly marked current. I inspected the actual files, checked the documented web and package links on 2026-10-24, and did not implement product code or rerun application test suites.

## Findings

1. **HIGH — Readiness does not define which capabilities are required versus optional.** **Location:** `PRODUCT_SPEC.md` FR-2 and Start a real run; `ARCHITECTURE.md` readiness criteria and `SENSOR_ENGINE.md` permission flow. The product says a run can continue without GPS or audio, but `prepare()` reaches `ready` only after selected sources and permissions are available. The documents do not say whether a denied GPS permission fails preparation, whether a selected-but-undecoded audio file enters `error`, or whether motion denial can be replaced by Manual mode without restarting preparation. An implementer can therefore produce a browser flow that contradicts the promised degraded run behavior. **Fix:** publish a capability matrix and make it part of the state contract. For example: Simulation and Manual require no browser permissions; DeviceMotion requires motion access unless the runner explicitly selects Manual; GPS is optional and denial yields `ready` with `pace/distance=unavailable`; audio is optional, while a selected file decode/worklet failure yields `error → saveWithoutAudio`. Define the `prepare()` result with per-capability states so `ready` does not mean every optional capability is active.

2. **HIGH — Local persistence failure has contradictory start behavior.** **Location:** `PRODUCT_SPEC.md` FR-2 and reliability requirements; `ARCHITECTURE.md` readiness criteria; `SENSOR_ENGINE.md` Loss and error policy. The readiness contract requires all local persistence objects, but the sensor policy says a storage failure leaves the live display running. That policy cannot also guarantee that local completion and interruption records survive the failure. **Fix:** choose one explicit rule. The safer first-release rule is `STORAGE_UNAVAILABLE` blocks `ready` with a retryable error and no run starts. If an unsaved run is intentionally supported, add an explicit `UNSAVED_LOCAL` mode, its UI warning, its completion semantics, and the privacy/history acceptance criteria instead of silently continuing.

3. **HIGH — The server is told to validate a best-pace claim it cannot verify from the permitted payload.** **Location:** `PRODUCT_SPEC.md` FR-11; `API_AND_DATA_MODEL.md` completion contract and privacy split. The completion request contains only `bestPaceSecPerM`, while raw GPS is never uploaded and aggregate samples may not be retained or may be too sparse to prove the fastest qualifying 30-second interval. Yet the API says the server must validate that the value is the fastest qualifying interval. **Fix:** choose a verifiable contract. Either make the client authoritative for the computed best pace and have the server validate only nullability, finite range, and session bounds, or send a privacy-preserving rolling-window summary sufficient for server verification and document its retention. Do not claim the server verifies the 30-second rule when the request contains no evidence for it.

4. **HIGH — Session settings snapshots omit settings that affect session behavior.** **Location:** `PRODUCT_SPEC.md` FR-9; `API_AND_DATA_MODEL.md` `UserPreferences`, `settingsSnapshot` schema, and preferences API. The preference model and defaults include `uploadAggregates`, `retainHistory`, and `batterySaver`, but the shared `settingsSnapshot` schema omits all three. The product says settings affect new sessions and each session stores a validated snapshot, so an active session cannot know which upload, retention, or battery policy it started with. **Fix:** add these fields, with exact defaults and cross-field rules, to the snapshot and `POST /api/sessions` contract, or explicitly classify them as global settings and define how an active session reads them. Use one shared schema for `UserPreferences`, the session snapshot, and the response type.

5. **HIGH — Prisma numeric types have no JSON wire representation.** **Location:** `API_AND_DATA_MODEL.md` Prisma schema and all session/history API examples. The schema uses `BigInt` for `activeDurationMs` and `Decimal` for pace, cadence, target, and sync values, while the examples show ordinary JSON numbers. A Next.js response that serializes Prisma `BigInt` directly throws, and Prisma `Decimal` values need an explicit conversion policy. **Fix:** define response DTO mappers and schemas. For example, convert bounded `activeDurationMs` to a JSON number because the documented maximum is safely below `Number.MAX_SAFE_INTEGER`, and convert Decimal values to either fixed-precision JSON numbers or strings consistently. State this representation for every create, completion, history, and metrics response and test the mapper without exposing Prisma objects.

6. **HIGH — The 200 MiB file limit does not bound decoded audio memory.** **Location:** `PRODUCT_SPEC.md` FR-6; `FEASIBILITY_REPORT.md` audio processing; `AUDIO_ENGINE.md` pipeline. A compressed 200 MiB file can decode to many hundreds of megabytes or more of PCM, especially for stereo and long-duration audio. The design decodes the file into an `AudioBuffer` before processing and has no maximum decoded bytes, duration, sample frames, or mobile-memory policy. This can make the advertised import path crash or kill the tab on the target devices. **Fix:** define a decoded-audio budget and enforce it before committing the file to the pipeline. Specify a trustworthy pre-decode duration/container check where available, a conservative compressed-file fallback, a post-decode `channels × frames × 4` cap, and the user-facing rejection code. If the product truly needs longer files, change the pipeline to bounded streaming/segment decoding rather than relying on the full `AudioBuffer` design.

7. **HIGH — The playlist score is declared nonnegative but can be negative.** **Location:** `PRODUCT_SPEC.md` FR-4 and `AUDIO_ENGINE.md` playlist score. For the current playable track with an exact BPM match, confidence `1`, no recency penalty, and `keepBiasBpm=4`, the specified score is `-4`, contradicting the requirement that `scoreBpm` be nonnegative. That changes the meaning of the relative-improvement denominator and makes the exact threshold behavior unclear. **Fix:** choose and document one formula. Either define `rawScoreBpm` and `scoreBpm = max(0, rawScoreBpm)` before comparison, or remove the nonnegative requirement and define the signed-score predicate, including how `max(currentScoreBpm, 1)` is intended to work. Also define the exact recency-penalty function rather than only its `0..6` range.

8. **MEDIUM — Playlist candidate eligibility is undefined when BPM is missing or low-confidence.** **Location:** `PRODUCT_SPEC.md` FR-4/FR-7; `AUDIO_ENGINE.md` candidate selection; `API_AND_DATA_MODEL.md` nullable `Track.sourceBpm`. Tracks may have `sourceBpm=null`, failed analysis, or confidence below `0.55`, but the matcher says it selects the lowest score among playable tracks. The formula cannot evaluate a null BPM, and “playable” is not defined as “has a valid BPM.” **Fix:** define `matcherEligible` explicitly, such as decoded/playable audio plus finite source BPM in `40..240`; allow low-confidence valid BPM with the documented confidence penalty and `Check BPM` UI, but exclude missing BPM until manual correction. Define the no-eligible-track result and its status instead of applying the unavailable penalty to an uncomputable score.

9. **MEDIUM — The metrics API does not have a complete, shared sample schema.** **Location:** `API_AND_DATA_MODEL.md` `RunningMetricsSample` and metrics endpoint; `ARCHITECTURE.md` route handlers. The endpoint prose says each sample has a status and source, but no status enum, field names, or allowed combinations are defined. The Prisma `syncStatus` is an unconstrained `String`, and `POST /api/sessions` says it validates `isSimulation`/`measurementSource` combinations without listing the matrix. This leaves room for a client to submit `isSimulation=false` with `SIMULATION`, arbitrary status text, or a manual sample that claims device confidence. **Fix:** publish a Zod `MetricsSample` schema and an enum such as `CALIBRATING`, `VALID`, `STALE`, `LOST`, `PAUSED`, `AUDIO_LIMITED`, and `MANUAL` as appropriate. Define the exact session-source matrix (`isSimulation=true` iff source is `SIMULATION`, etc.), allowed null/value/status combinations, and use an enum or validated bounded field in persistence.

10. **MEDIUM — The documented API surface is not represented in the architecture repository shape.** **Location:** `ARCHITECTURE.md` repository shape; `API_AND_DATA_MODEL.md` history, playlist, track, and playback-event APIs. The architecture lists only collection route files for history and playlists and no track routes, while the API contract requires `/api/history/:id`, `/api/playlists/:id`, `/api/tracks`, and optionally `/api/sessions/:id/playback-events`. The roadmap also expects a Track metadata API client and playlist CRUD. **Fix:** list every dynamic route and method in the repository shape, including the exact ownership and validation module for each, or explicitly state that the routes are consolidated behind another handler. The implementation roadmap and API contract must point to the same paths.

11. **MEDIUM — Turning off retention can delete the active server session before completion.** **Location:** `PRODUCT_SPEC.md` FR-9/FR-10; `API_AND_DATA_MODEL.md` retention update; `ARCHITECTURE.md` completion flow. `retainHistory=false` is described as immediately deleting all server sessions, while settings changes otherwise affect new sessions. If changed during an active run, the later completion or interruption request can receive `404` after its session row was deleted, and the client’s snapshot may still say retention was enabled. **Fix:** either disable this setting while a session is active, or define a transactionally consistent policy: mark the active session for deletion, let completion finish locally without server history, then delete it and its queued uploads. Specify what the UI reports and how retries behave in both cases.

12. **MEDIUM — Anonymous local library persistence is not designed beyond transient object URLs.** **Location:** `PRODUCT_SPEC.md` anonymous local library behavior and FR-6; `AUDIO_ENGINE.md` `AudioSource.objectUrl`; `tasks.md` M5.1. An object URL is not durable across reloads, yet the product promises local library behavior and the server never stores audio bytes. The design does not define an IndexedDB/blob record, rehydration, quota handling, eviction, or the order for revoking URLs and deleting the underlying blob. **Fix:** specify the local record (`clientAssetId`, Blob, metadata, schema version, byte count), quota/error behavior, reload rehydration that creates a fresh object URL, and deletion/cleanup semantics. Keep the transient URL out of persisted state and make the local-only path independently testable.

13. **MEDIUM — A cited lifecycle source is currently dead.** **Location:** `FEASIBILITY_REPORT.md` Lifecycle and background execution. On 2026-10-24, `https://developer.mozilla.org/en-US/docs/Web/API/Page_Lifecycle_API` returned 404. The linked Chrome page is reachable, but the document presents both as supporting sources. **Fix:** replace the dead MDN URL with a current canonical source or remove it, record the checked date, and recheck source links during implementation and release. Do not leave a 404 citation in the research that gates browser behavior.

14. **MEDIUM — The dependency audit omits the required Auth.js dependency and uses weak maintenance evidence.** **Location:** `PRODUCT_SPEC.md` authentication assumption; `ARCHITECTURE.md` Auth.js boundary; `FEASIBILITY_REPORT.md` dependency table. Auth.js/its chosen package is required for production authentication but has no version, license, repository, browser/server role, or maintenance entry. For the listed packages, “npm version published; active upstream repo” is a conclusion rather than dated release/maintenance evidence, and GSAP remains conditional on a future legal decision even though it is in the locked stack. **Fix:** add the exact Auth.js package(s) and version, license, canonical source, server-runtime compatibility, and maintenance evidence. For every dependency and bundled font, record the check date, exact release date, repository activity or support policy, license terms, and decision. Make GSAP either legally approved with its standard-license scope or replace it before calling the stack locked.

15. **MEDIUM — The tertiary text token fails the stated normal-text contrast target.** **Location:** `DESIGN_SYSTEM.md` color tokens and accessibility section. `--pulse-dim: #756E78` against `--pulse-void: #0A080D` has approximately 4.04:1 contrast, below the stated 4.5:1 WCAG AA target for normal text. The token is explicitly allowed for tertiary text, so “never the sole status signal” does not solve the contrast failure. **Fix:** change the token to a value meeting 4.5:1 for every intended text background, or prohibit it for text and restrict it to non-text decoration with a semantic token name that cannot be used for labels or instructions. Recalculate contrast for each semantic foreground/background pairing, not only the page background.

16. **MEDIUM — GPS rejection and jump-validation rules are not deterministic.** **Location:** `FEASIBILITY_REPORT.md` GPS decision; `SENSOR_ENGINE.md` GPS pace and distance. The documents say accuracy over 100 m is rejected for pace but do not say whether that point may advance distance, while the sensor design says poor accuracy must not advance invalid distance. “Unless a sustained sequence supports it” for jumps over 8 m/s has no sample count or duration. **Fix:** choose one acceptance rule for both distance and pace, then specify the sustained-jump evidence, such as three consecutive fixes spanning at least five seconds with accuracy <= the configured limit. Define segment reset behavior and test the exact boundary cases.

17. **MEDIUM — History aggregate calculations are not reproducible.** **Location:** `PRODUCT_SPEC.md` history journey and FR-11; `API_AND_DATA_MODEL.md` completion fields. Best pace and sync have detailed rules, but average pace, average cadence, average target BPM, and the relationship between cumulative distance and active duration do not define whether aggregation is time-weighted, sample-weighted, or based on accepted intervals. Different clients can therefore produce different history for the same run. **Fix:** specify interval weighting and exclusions for every aggregate. For example, time-weight each cadence/target sample by its valid interval, calculate average pace from accepted distance over valid active time, and define behavior for gaps, pause, lost GPS, and no valid samples. Version the aggregation formula alongside `sync-v1` if it is persisted.

18. **MEDIUM — The one-decimal BPM input rule is not enforced by the shared validation contract.** **Location:** `PRODUCT_SPEC.md` FR-7; `AUDIO_ENGINE.md` validation; `API_AND_DATA_MODEL.md` shared limits. The prose requires manual correction to have one decimal precision, but the shown Zod rules and general API limits only require a finite value in `40..240`, so values such as `123.456` are accepted. Database precision `Decimal(7,2)` also does not enforce one decimal. **Fix:** add an explicit precision rule such as `Number.isInteger(value * 10)` after finite/range validation, apply it to manual corrections and any API field that promises one decimal, and return a field-level validation error when it fails.

## Preparation dispositions

- **Finding 15:** The foundation corrected `--pulse-dim` to `#9D939E` in `app/globals.css` and `DESIGN_SYSTEM.md`, superseding the earlier below-target `#756E78` draft token. The overall design verdict remains `CHANGES_REQUESTED` because the other findings are still unresolved.

## Verified Assumptions

- **Historical review snapshot (2026-10-24):** The repository had no current PULSE implementation. The working tree contained the old AskMongo Vite/Express/MongoDB files as deletions and the PULSE documents/tasks as untracked preparation artifacts; the committed tree contained the unrelated AskMongo baseline, not the planned Next.js product. No planned source, API, Prisma schema, worklet, sensor adapter, or test was treated as implemented.
- **Current repository state:** The PULSE preparation foundation and its required documents are present, including the Next.js root, accessible primitives, runtime-agnostic boundary files, foundation tests, `tasks.md`, and the root Codex handoff. The old AskMongo files remain intentionally deleted. No main PULSE product routes, sensors, audio processing, database workflows, or API workflows are implemented, and M1–M10 remain planned/incomplete.
- All seven requested design documents and `tasks.md` were read. The roadmap covers M1 through M10 with objectives, dependencies, outputs, acceptance criteria, verification, priority, and complexity.
- The Kelvin reference URL was reachable during this review. `DESIGN_SYSTEM.md` records typography, hierarchy, palette, grid, motion, responsive behavior, and an explicit original-interpretation/no-copy rule. The repository contains no PULSE implementation or copied Kelvin asset to inspect.
- The documents consistently distinguish cadence as `steps/min` from pace as time per distance, use meters and seconds-per-meter internally, define the `1:1`, `2:1`, and `1:2` beat-to-step ratios, and represent lost cadence as `null` rather than zero.
- Simulation is specified as deterministic, seeded, permission-free, visibly labeled, and routed through the same source/session/target/audio ports intended for real adapters. It does not claim that a visual or surrogate simulation is real pitch-preserving DSP.
- The browser/native boundary is generally honest: foreground motion, GPS, local decoding, and AudioWorklet processing are capability- or permission-gated; background/lock-screen behavior and third-party stream processing are explicitly limited or out of scope; native is identified for reliable background behavior.
- The documents provide typed module boundaries, injectable clocks and browser/audio/storage ports, failure codes, local-first handling of raw motion/location/audio, aggregate-only server synchronization, user-scoped PostgreSQL/Prisma persistence, and broad accessibility requirements including reduced motion, text equivalents, focus, keyboard operation, 44px controls, 320px layout, and 200% zoom.
- The documented replacement motion-permission URL is reachable, as are the Kelvin, sensor, Web Audio, streaming, and listed license URLs checked during review. The Page Lifecycle MDN URL is the exception documented in finding 13.
- Registry checks on the dated candidate versions confirmed the existence and reported licenses for key entries including Next, React, Tailwind, GSAP, Motion, Zustand, Zod, Prisma, SoundTouchJS, and the three Fontsource candidates. These checks do not establish real-device quality or prove the design’s generic “active upstream repo” maintenance claims.

## Unverified/Wrong Assumptions

- No implementation evidence exists for cadence accuracy, GPS behavior, pitch preservation, AudioWorklet render budget, underrun rates, browser permission behavior, background recovery, battery use, or accessibility behavior. The documents correctly identify device testing as a future gate, but those claims remain unverified.
- The Page Lifecycle MDN citation is wrong/stale as written because it returned 404 on the review date. The reachable Chrome lifecycle source does not make the MDN URL valid.
- Auth.js is described as available in the architecture but is absent from the dependency/license/maintenance record. Its package choice, version, and integration behavior must not be silently invented by implementation.
- The design’s privacy statement that no raw GPS/motion/audio is uploaded is compatible with the proposed aggregate model, but it does not by itself make the client-computed best-pace value server-verifiable. That is an unresolved contract choice described in finding 3.
- The old AskMongo files are not evidence that PULSE can run today. The preparation documents explicitly describe the Next.js application, browser adapters, database, worklet, and tests as future Codex outputs.

**Verdict:** CHANGES_REQUESTED. The HIGH and MEDIUM findings above leave unresolved state behavior, API serialization/validation, privacy semantics, audio feasibility limits, source validity, and accessibility requirements.
